# 通信障害の調査用ログ

[READMEへ戻る](../README.md)

[`scripts/zenoh-capture.sh`](../scripts/zenoh-capture.sh)で、Zenohログ・TCP接続・通信量・PC負荷・pingをまとめて保存する。中央・車載・制御PCで同時に記録すると、異常発生時刻を比較できる。

## 実行方法

Ubuntu 22.04上で、リポジトリのディレクトリから通常ユーザーで実行する。必要なsudo認証はスクリプト内で行う。

```bash
./scripts/zenoh-capture.sh
```

- 記録時間：3600秒（1時間）
- 保存先：`~/zenoh-logs/zenoh-<ホスト名>-<JST日時>-<識別子>/`
- 終了方法：時間経過による自動終了、または`Ctrl+C`

実行中はターミナルを開いたままにする。通常終了・Ctrl+C時には、生成したログフォルダの所有者を実行ユーザーへ戻す。電源断や`kill -9`では終了処理は実行されない。

時間・保存先を指定する場合：

```bash
# 10分間記録
./scripts/zenoh-capture.sh 600

# 1時間記録し、保存先を指定
./scripts/zenoh-capture.sh 3600 "$HOME/zenoh-logs"
```

記録時間は1〜86400秒で指定する。スクリプトはリポジトリ内から直接実行でき、ログ取得のための`make update`は不要。

## 記録内容

| ファイル | 内容 |
|---|---|
| `metadata.txt` | 開始時の時刻同期、IP・経路、router状態、パッケージ情報 |
| `router.log` | 開始5分前からのrouterログと、記録中の追加ログ |
| `tcp.log` | TCP 7447の接続、送受信キュー、RTT、再送情報。約1秒間隔 |
| `network.log` | 各NICの累積送受信量・drop数。約1秒間隔 |
| `process.log` | routerのプロセス情報、CPU累積値、システム負荷。約5秒間隔 |
| `ping-<IP>.log` | 対象PCへのping。約1秒間隔 |
| 設定ファイル | 読み取り可能な配置済み設定のコピー |

時刻は原則UTCで記録する。日本時間はUTCに9時間加算する。pingの`-D`時刻はUNIX時刻。

NICの通信量には、LiDARなどZenoh以外の通信も含まれる。TCP再送数やNICのカウンタは累積値なので、記録中の増分で判断する。`ps`のCPU使用率はプロセス起動後の平均値。

各継続ログは32MiBごとに切り替え、現行ファイルと過去15世代（合計16ファイル）を保存する。継続ログの合計は1回あたり約5GiBが目安で、別途メタデータ・設定コピーが加わる。上限を超えると古い世代は削除される。過去の実行フォルダは自動削除しない。

## ping対象の設定

現在のスクリプトは次のIP構成を前提とする。

| 実行PCのIP | ping対象 |
|---|---|
| `192.168.1.70`（中央） | `192.168.20.73`、`192.168.20.119` |
| `192.168.20.73`（車載） | `192.168.1.70`、`192.168.20.119` |
| 上記以外（制御PCを想定） | `192.168.1.70`、`192.168.20.73` |

**ping対象は`deployment.env`から自動取得しない。** 別のIP構成で使う場合は、スクリプト末尾のIP判定と`targets`を変更する。

## 障害を再現するとき

1. 各PCの時刻同期を確認し、関係するPCでログ取得を開始する。
2. 機体の安全を確保して実際のプログラムを動かす。
3. ノード起動・終了、RVizでの購読開始、異常発生などの操作・発生時刻をメモする。
4. 異常発生後、安全上支障がなければ再起動前に1〜2分記録を続ける。
5. `Ctrl+C`で取得を終了し、各PCの出力フォルダと操作メモを保存する。

まず実際のプログラムで記録し、特定の通信が原因として疑われた段階で、テスト用プログラムによる比較を行う。

スクリプトはrouterの再起動・設定変更やROSのTopic配信・Action Goal送信を行わない。疎通確認用のpingは送信する。スクリプトをCtrl+Cで終了しても、routerやROSノードは停止しない。

Actionサーバの探索状態、Rajant内部の無線状態、パケットキャプチャ、ROSノードの標準出力は取得対象外。ROSノード側に表示されたエラーは、別途ログや画面を保存する。TCP接続が維持されていても、ROS通信の正常性を保証するものではない。

## ログを読めない場合

終了後もroot所有のままの場合は、通常ユーザーのターミナルで、実際の出力フォルダを指定して所有者を戻す。

```bash
# 下のパスを、実際の出力フォルダに置き換える
sudo chown -R "$(id -u):$(id -g)" "$HOME/zenoh-logs/zenoh-<ホスト名>-<JST日時>-<識別子>"
```

旧版で親フォルダ`~/zenoh-logs`がroot所有になっている場合は、親フォルダ自体も修正する。

```bash
sudo chown "$(id -u):$(id -g)" "$HOME/zenoh-logs"
```

`router.log`が空でも、対象期間にログ出力がなければ正常。権限不足のメッセージがある場合は、sudo認証を伴う実行になっているか確認する。


## 中央PCの性能と動的な接続先の記録

既存のnetwork.log・process.log・固定2対象のpingを維持し、capture-metrics.pyを併用する。スクリプト2本は同じscriptsディレクトリに配置する。

| 追加・拡張ファイル | 記録内容 |
|---|---|
| tcp.log | 従来のss情報にソケット識別情報を追加。約1秒間隔 |
| peers.jsonl | TCP 7447の接続先を自動検出。接続単位の送受信カウンター・差分・bps、RTT、再送、キュー、接続/切断/再接続、動的ping |
| performance.jsonl | 約5秒間隔。コア別CPU・割り込み・softnet・TCP全体統計・メモリ/swap・PSI・ディスクI/O・NICリンク情報・qdisc・ルーターのスレッドCPUカウンター/FD数/上限・採取プロセス自身の統計 |
| kernel.log | 開始5分前からのカーネルイベント。OOM、NIC異常など |
| metrics-status.jsonl | 採取開始/終了、ss失敗、1秒を超える採取遅延 |
| capture-status.log | journalctlと保存処理の終了コード。124は指定時間経過による終了。短い実行状態の記録 |

NICドライバー統計はethtoolがある場合に開始時に保存する。詳細項目が非対応・権限不足の場合はunavailableまたはコマンドエラーを残す。NIC・OSの継続カウンターは各サンプルの差分で読む。CPU上位プロセスのpcpuは起動後平均で、区間使用率ではない。

### DHCPと切断後の追跡

IPの事前登録は不要。ESTABで観測した相手を追跡し、切断後も既定300秒間、約10秒間隔でpingする（同時実行最大4件）。再接続時は追跡を継続する。既存の固定ping対象は重複してpingしない。静的pingは従来どおり記録期間全体で継続する。

追跡時間は第3引数で指定する。例：1時間採取し、切断後10分追跡する。

```bash
./scripts/zenoh-capture.sh 3600 "$HOME/zenoh-logs" 600
```

追跡は採取の終了時に終了する。0秒なら切断後の動的追跡を行わない。切断履歴はログの保存世代内に残る。IP変更後は新しいIPとして自動検出し、旧IPも期限まで追跡する。同じ物理PCという運用上の仮定はできるが、別IPの統計を自動的に同一PCへ合算しない。ping無応答だけでPC停止とは断定しない。

TCP情報は接続単位。再接続やソケット識別情報が取れない場合の差分は不明として扱い、カウンターの巻き戻りを通信量に加算しない。ss取得失敗は欠測として記録し、全相手の切断とは扱わない。1秒未満の接続は取り逃す場合がある。

### 性能の読み方と限界

- CPU：コア別・スレッド別カウンターの差分で飽和を確認。CPU全体平均だけで判断しない。guest/guest_niceはuser/niceに含まれるため二重加算しない。
- メモリ：MemAvailable、swapの増減、PSIを合わせて不足を判断する。
- Ethernet：方向別にバイト増分×8÷経過秒でbpsを求め、リンク速度で割って使用率にする。全二重の送受信は合算しない。速度が不明・0・負値なら使用率は算出しない。仮想NICの速度は実効上限とは限らない。
- dropや再送は累積値の増分で確認。softnet、割り込み、qdiscとCPUを照合し、中央内部の詰まりと接続先別の悪化を切り分ける。
- 時刻補正に備え、追加JSONにはUTCと単調増加時計を保存する。CPU/通信量の差分には単調増加時計を使用する。

全topicの購読、全パケット保存、Zenoh管理空間の問い合わせ、ログレベル変更は行わない。中央を通らない通信、相手PC内部、無線・スイッチ内部、topicごとの配信成功は分からない。既存2対象に加えて動的ping分の小さな通信が発生する。採取負荷は機器と接続数に依存し、性能ログ内の採取プロセス情報と欠測記録で確認する。
